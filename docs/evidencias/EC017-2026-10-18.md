# Evidencia EC017 — Reprocesamiento masivo nocturno de perfiles en RISK (HA-ESC-004)

- **Fecha:** 2026-10-18
- **Historia de arquitectura:** HA-ESC-004 (reprocesar fuera de horario pico sin degradar el tráfico en línea)
- **Escenario EC017:** ≥ 10.000.000 de perfiles en < 2 h (~1.389 perfiles/s) con el p95 en línea de EC003 ≤ 400 ms
- **Artefactos:** [`infra/batch.tf`](../../infra/batch.tf), `services/risk/app/batch_reproceso.py`, [`scripts/sembrar_perfiles.py`](../../scripts/sembrar_perfiles.py)

> **ESTADO: PENDIENTE DE MEDIR.** Este informe **no trae ninguna cifra de caudal**: una versión anterior las traía, pero eran
> inventadas (el script de siembra calculaba la «medición» a partir de un número escrito a mano) y se retiraron. Lo que sí
> está hecho y verificado es la implementación; falta correr la prueba.

## 1. Lo implementado y verificado

| Pieza | Estado |
|---|---|
| Batch idempotente por lotes (`python -m app.batch_reproceso`) | ✅ pruebas en `services/risk/tests/test_batch_reproceso.py` |
| **Reparto entre tareas** (`CLOUD_RUN_TASK_INDEX` / `CLOUD_RUN_TASK_COUNT`, hash de `cliente_id`) | ✅ implementado en esta rama; el filtro se prueba en pytest. **Falta** comprobar contra MongoDB real que las particiones son disjuntas y cubren todo |
| Cloud Run Job + Cloud Scheduler (`infra/batch.tf`), `task_count` configurable (`batch_tareas`, default 1) | ✅ definido; no desplegado |
| `scripts/sembrar_perfiles.py`: siembra por la API real de RISK y reporta lo que midió | ✅ reescrito (antes apuntaba a un endpoint que no existe) |

La proyección a 10 M **requiere** el reparto entre tareas: con `task_count = 1` una sola tarea tendría que sostener
1.389 perfiles/s.

## 2. Cómo medirlo (reducido, regla 2 del plan)

```bash
# 1. Sembrar unos miles de perfiles por la API real de RISK (imprime el caudal de siembra que midió)
python scripts/sembrar_perfiles.py --risk-url http://localhost:8002 --total 5000 --hilos 8
# 2. «Envejecerlos» para que el batch tenga trabajo
docker compose exec -T mongo1 mongosh --quiet --eval 'db.getSiblingDB("risk").perfiles.updateMany({cliente_id: /^cli-ec017-/}, {$set: {version_reglas: "v0-semilla"}})'
# 3. Correr el batch y leer sus métricas (perfiles_por_segundo)
docker compose run --rm risk python -m app.batch_reproceso
# 4. Con tráfico en línea en paralelo (k6) para ver el efecto sobre el p95 de EC003
```

Con el `perfiles_por_segundo` **medido** de una tarea, la regla de tres da cuántas tareas hacen falta:
`ceil(1.389 / caudal_de_una_tarea)`, que se fija en `batch_tareas`. Ese cálculo se anota aquí **con el caudal medido**, y la
medición en staging (Atlas M0, otro disco) puede dar un valor distinto del local.
