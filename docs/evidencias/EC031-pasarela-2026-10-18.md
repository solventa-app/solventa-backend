- **Fecha:** 2026-10-18
- **Historia de arquitectura:** HA-MOD-001 (capa anticorrupción) · **HU:** HU-W05 (KAN-28)
- **Escenario:** EC031, «se cambia el proveedor de pagos»; medida: exactamente 0 líneas alteradas en los componentes del Core.
- **Estado:** verificado con pruebas automáticas locales. **La corrida de punta a punta con el stack levantado está

## 1. Qué se hizo

Un segundo adaptador, `AdaptadorPasarelaAlterna` (`services/acl-worker/app/adapters/pasarela_alterna.py`), que habla con un
proveedor de **otra API**: otras rutas (`/alterna/v2/charges`), otros campos (`reference`, `payment_token`, `policy`) y otros
estados (`APPROVED`, `DECLINED`, `PENDING`). Se elige con `PROVEEDOR_PASARELA=alterna`. El stub de la pasarela expone esa
segunda API sobre la misma memoria de cobros y los mismos modos de falla.

## 2. Dónde está el cambio

| Archivo | Cambio |
|---|---|
| `services/acl-worker/app/adapters/pasarela_alterna.py` | **Nuevo**: el adaptador |
| `services/acl-worker/app/main.py` | 8 líneas: elegir el adaptador por configuración |
| `services/acl-worker/app/application/configuracion.py` | la variable `PROVEEDOR_PASARELA` |
| `stubs/pasarela/app/main.py` | las rutas del segundo proveedor simulado |
| `services/acl-worker/tests/test_ec031_pasarela.py`, `stubs/pasarela/tests/test_alterna.py` | pruebas |

El Core que usa la pasarela es PAYMENTS (y el BFF que lo llama). Para este cambio **no se tocó** ninguno de los archivos con
que PAYMENTS habla con el ACL: `services/payments/app/application/cliente_acl.py` y `conciliacion.py`, ni
`services/bff/` (todo el BFF). Se puede comprobar:

```bash
git diff origin/develop...HEAD --stat -- services/bff \
  services/payments/app/application/cliente_acl.py services/payments/app/application/conciliacion.py
# sin salida = 0 líneas
```

Nota de transparencia: esta misma rama sí modifica otros archivos de PAYMENTS, pero por **otros** cambios de HU-W05 (cifrado
del token, reintento por Cloud Tasks, cobros atascados), no por el cambio de proveedor.
