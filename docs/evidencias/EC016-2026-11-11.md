## 2. Cómo se midió

Stack local: `docker compose --profile servicios up -d --build --wait claims policy payments` (trae también sus
dependencias: `postgres`, `mongo1`/`mongo2` con réplica, `auth`, `almacenamiento`, `fake-gcs`) y
`docker compose --profile servicios --profile semilla run --rm sembrar-polizas-parametricas` antes de correr k6.

> **Nota del entorno:** el `docker build` de las imágenes falló inicialmente por una intercepción TLS de la red de
> este sandbox hacia `pypi.org` durante `pip install` (no relacionada con el código del repo). Se resolvió
> agregando temporalmente, solo en este sandbox y solo para poder construir las imágenes, el certificado de la
> CA del proxy del entorno a los Dockerfiles de `claims`, `policy`, `payments`, `auth` y `almacenamiento`; esos
> Dockerfiles se revirtieron a su versión original al terminar esta corrida (no quedó ningún cambio en
> `services/` en el árbol de trabajo). Es un problema de este sandbox, no del repo ni de staging/CI.

Guion nuevo `tests/k6/ec016-ingesta-parametrica.js` (adaptado al estilo de los guiones existentes en `tests/k6/`,
sin `lib/` nuevo porque no reutiliza sesión ni GraphQL: habla HTTP directo con CLAIMS). Genera eventos
`evento.parametrico.recibido` sintéticos, válidos contra `contracts/events/evento.parametrico.recibido.schema.json`,
con `eventoId` único (UUID v4) por evento. El 2 % (`FRACCION_CALZA=0.02`, decisión de diseño declarada en el guion)
cae sobre el umbral real de la semilla (vuelo `AV9340:2026-11-11` con retraso 120-300 min, o celda `4.62,-74.09`
con `PRECIPITACION_MM` 50-150 mm) para generar un siniestro real; el 98 % restante son vuelos/celdas sin cobertura
o bajo el umbral (incluido el vuelo `AV1234`, que sí tiene póliza pero con un retraso sintético bajo 100 min).

```bash
# 1. Stack mínimo + semilla
docker compose --profile servicios up -d --build --wait claims policy payments
docker compose --profile servicios --profile semilla run --rm sembrar-polizas-parametricas

# 2. Prueba de humo (200 eventos / 20 s) y de capacidad (5.000 eventos / 30 s) antes de la corrida completa
docker run --rm -i --network host -v "$PWD":/work -w /work \
  -e CLAIMS_URL=http://localhost:8012 -e EVENTOS_TOTAL=200 -e DURACION_INGESTA=20s \
  grafana/k6:latest run tests/k6/ec016-ingesta-parametrica.js

# 3. Corrida completa: escala de D9 (100.000 eventos en 10 min, 167 eventos/s sostenidos)
docker run --rm -i --network host -v "$PWD":/work -w /work \
  -e CLAIMS_URL=http://localhost:8012 -e EVENTOS_TOTAL=100000 -e DURACION_INGESTA=10m \
  -e RESUMEN_JSON=tests/k6/resultados-crudos/ec016-ingesta-parametrica-2026-11-11.json \
  grafana/k6:latest run tests/k6/ec016-ingesta-parametrica.js
```

Todo corrió **una sola vez** a la escala completa (más dos corridas previas pequeñas de humo/capacidad, 200 y 5.010
eventos, que no se reportan como la medición oficial, solo como validación de que el guion y el stack sostenían la
tasa antes de comprometer 10 minutos). Una corrida no es una muestra estadística repetida; el p95/p99 que sigue
viene de 100.192 peticiones HTTP individuales dentro de esa única corrida, no de repetir la corrida completa varias
veces.

## 3. Resultados

### 3.1 Cero pérdida (lo pedido por la sección C del plan: publicados = procesados + en DLQ)

| Métrica | Valor medido |
|---|---|
| Eventos publicados (HTTP `POST /eventos/parametricos`) | **100.192** (k6 corrió a tasa constante 10 min; el conteo real de iteraciones completadas) |
| Aceptados por CLAIMS (200) | **100.192** |
| Fallidos (5xx, timeout, cualquier código distinto de 200/429/503) | **0** |
| Contrapresión explícita (429/503) | **0** (CLAIMS nunca llegó a necesitarla a esta carga) |
| **Pérdida** (`publicados - aceptados - fallidos - contrapresión`) | **0** |
| Siniestros paramétricos creados | **2.027** (de los 100.192 eventos; ≈ 2,02 %, consistente con `FRACCION_CALZA=0,02`) |

**Sin DLQ real que observar** (no hay Pub/Sub en este entorno): "cero pérdida" aquí significa que el 100 % de las
peticiones HTTP que k6 mandó recibió una respuesta de CLAIMS, y esa respuesta fue siempre 200 (aceptado), nunca un
error silencioso. **CLAIMS no implementó ninguna contrapresión explícita (429/503) propia**: a esta carga (167
eventos/s sostenidos) nunca lo necesitó, así que no se pudo observar ese comportamiento (ni el que el plan aspira,
ni ningún otro); FastAPI/Uvicorn simplemente atendió todo. Si CLAIMS se saturara en staging con Cloud Run, el
comportamiento real (colas de Uvicorn, instancias y concurrencia de Cloud Run, reintentos de Pub/Sub) es distinto al
de este proceso único en un contenedor local y **no se midió aquí**.

**Verificación cruzada contra la base real** (no solo la respuesta HTTP): se contaron los documentos de
`claims.siniestros` con `origen: "PARAMETRICO"` después de la corrida completa y de las dos corridas de humo
previas (200 + 5.010 eventos, con la misma `FRACCION_CALZA`): **2.125** siniestros en total en la base, que
coincide con la suma de `creados` reportada por las tres corridas (2 + 95 + 2.027 + 1 de una prueba manual anterior
con `curl` = 2.125). Las órdenes de pago en PAYMENTS (`indemnizaciones`) también son **2.125**: exactamente una por
siniestro, **0 duplicadas**, confirmando la idempotencia por `eventoId` bajo esta carga sostenida.

### 3.3 Efecto sobre el camino síncrono del BFF — NO MEDIDO (limitación declarada)

El encargo permite, si no es viable correr dos procesos k6 a la vez en este sandbox, medir solo la ingesta y dejar
explícito que falta la medición simultánea. **Eso es lo que pasó aquí:** para esta corrida solo se levantaron
`claims`, `policy`, `payments` y sus dependencias (Postgres, MongoDB, `auth`, `almacenamiento`, `fake-gcs`); **no se
levantó el BFF, el gateway, el ACL Worker ni los stubs de fuentes**, así que no hay ningún camino síncrono de EC003
corriendo en este entorno para medir en paralelo. Levantar el stack completo y correr `perfilamiento-baseline.js`
(EC003) al mismo tiempo que este guion queda **pendiente**; dado que la ingesta paramétrica, aquí, usó una fracción
pequeña de una máquina de 4 CPUs (sección 3.2), es razonable esperar que no degradaría EC003, pero esa es una
expectativa, no una medición, y no se reporta como tal.

## 4. Proyección hacia 1.000.000 de eventos (regla de tres) y lo que NO se puede concluir

Con la tasa **medida** y sostenida sin pérdida (167 eventos/s durante 10 minutos completos, 100.192 eventos reales),
1.000.000 de eventos a la misma tasa tomarían `1.000.000 / 167 ≈ 5.988 s ≈ 1 h 40 min`. Esto es una proyección
lineal simple y **no está medida**:

- **No se probó la tasa más alta.** Solo se confirmó que el sistema sostiene 167 eventos/s (el objetivo de D9) sin
  degradarse visiblemente (latencias y uso de CPU/memoria bajos); no se exploró dónde está el techo real de esta
  máquina ni el de Cloud Run en staging.
- **Una hora y 40 minutos de carga sostenida no se corrió.** Con 10 minutos no se puede saber si MongoDB (con solo
  2 nodos de réplica aquí, sin el tercero de un replica set de producción) o Postgres degradan con una colección o
  tabla mucho más grande, igual que advierte `EC017-2026-10-18.md` para el batch de RISK.
  - Mongo tiene 2.125 documentos nuevos tras esta corrida: lejos de un volumen que no entre en memoria.
- **Las APIs reales (Open-Meteo, AviationStack) no entran en esta medición** (como ya anticipaba la sección G del
  plan): esto mide el tramo ACL→CLAIMS sustituido por HTTP directo, no la capacidad real de esas APIs gratuitas,
  que ni de lejos sostienen 100.000 ni 1.000.000 de consultas.
- **Sin Pub/Sub real**, no se midió el comportamiento de reintentos, backoff ni DLQ bajo carga, que es justo lo que
  la sección C del plan pide ("publicados = procesados + en DLQ"); aquí "publicados" y "procesados" son lo mismo
  porque no hay una cola real entre el publicador y CLAIMS.
- **Una sola corrida.** No hay repeticiones de la corrida completa de 10 minutos para ver variación entre corridas
  (sí hay 100.192 muestras dentro de esa única corrida, que es lo que respalda el p95/p99 de la sección 3.2).
